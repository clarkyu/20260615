## 三、逐阶段详解

### 阶段 0 · MVP 与快速成形（#1–#22，06-15）
**做了什么**：从零搭出可用应用——录制提交 + AI 评阅 + 按班级导出（#1）；批量建授课、批量发作业、班级/学期/状态筛选（#2–5）；登录体系（学校下拉 + 工号登录 + 密码显隐，#6–7、#14–15）；规范化院系/专业/手机号（#8）；修 D1 事务导致的发布失败（#9）；改名「你好！作业 / Hi, Homework」、切域名 hihomework.com（#16–18）；作业的提交类型（文本/音频/视频）、分类、手写提交（#19–22）。
**有什么用**：把核心业务闭环（建班→发作业→学生交→老师批→导出）一次性立起来。
**可改善**：这阶段是「能跑」优先，#9（D1 事务）和后面要修的 IDOR（#28）说明早期对 Cloudflare D1 限制和多租户授权的考量不足——属于 MVP 必然，后续阶段已系统补课。

### 阶段 1 · 五段式重构（#23–#27，06-15~16）
**做了什么**：评分领域层 + AI 置信度分流地基（#23）；学生即时学练闭环（#24）；老师「AI 先批、只看例外」（#25）；学情分析（#26）；AI 备课出题（#27）。
**有什么用**：确立了产品的差异化骨架——「AI 先评、老师按例外复核」，是后续一切评分/学情功能的基础。
**可改善**：置信度阈值（`REVIEW_CONFIDENCE_THRESHOLD=0.85`）是经验值、写死在代码里，缺真实数据校准；备课出题（#27）后续用得较少，可评估投入产出。

### 阶段 2 · 质量审查 + 上手（#28–#32，06-16）
**做了什么**：代码质量审查修复（媒体管线 / **IDOR** / 置信度 / 健壮性，#28）；老师上手三步引导、手动建班（#29）；教学默认值与「平时/测试成绩」分开（#30–32）。
**有什么用**：第一次系统性堵漏 + 降低老师上手门槛。
**可改善**：#28 已修一批 IDOR，但**校内按 id 越权**直到 #192 才彻底修——说明授权校验当时是「逐点修」而非「集中策略 + 回归测试」，留下了同类隐患。

### 阶段 3 · 题库系统（#33–#41，06-16）
**做了什么**：题库 + 跟读句集管理（#33）；三段式句子（中心句/解释句/情境例句，#34）；从题库发布 + 学生竖屏跟读（#35）；题库可编辑（#36）；逐句录音逐句提交（#37）；一键复习薄弱句（#38）；逐句 AI 评分（#40）；全班成绩单 + 导出（#41）。
**有什么用**：把「跟读」做成可复用的教学内容资产，支撑后续 2000 句官方题库。
**可改善**：逐句评分的加权（accuracy 0.7 / completeness 0.3）同样是经验值；题库与作业的耦合点较多，后续多环节作业（阶段 9）才理顺。

### 阶段 4 · UI + 校验地基（#42–#46，06-16）
**做了什么**：暗色模式 + 中文字体 + 恢复缩放（#42）；骨架屏 + 进步高光 + a11y 入口（#43）；**zod 校验**铺到名册/内容/作业/批改/账号各 action（#44–46）。
**有什么用**：建立「所有 action 输入过 zod」这条可信边界——后续安全的基石之一。
**可改善**：a11y 在 #43 只是「入口」，真正系统化要到第二波（#194–196）。

### 阶段 5 · 异步批改 + 分层重构（#47–#61，06-16）★架构核心
**做了什么**：持久批改任务 + 有界重试 + 自愈（#47，durable grading）；**分层重构** action→domain→repo（#48–52，含最大一支「学生名册」#51）；架构归档为 Skill（#53）；**lint 强约束**禁止 action 直接碰 prisma（#54）；页面只读查询全部收进仓储（#55–60）；auth 资料更新收口（#61）。
**有什么用**：这是整个项目可维护性的转折点——多租户 scoping 集中到 repo 层、配置集中到 config.ts、批改不再「尽力而为」。后续所有功能都受益于这套分层。
**可改善**：分层很干净，但**没有集成/E2E 测试**——验证靠 tsc/lint/单测/build，repo 层的多租户 scoping 主要靠单测断言 `where` 形状，缺真实 D1 端到端验证。

### 阶段 6 · 安全 + 代码评审（#62–#72，06-16）

**有什么用**：把一批正确性/安全/健壮性问题成批清掉，并补上关键单测。
**可改善**：评审是「一轮密集修」，说明缺少持续的静态分析/安全门禁（CI 只有 lint+tsc+test+build，无 SAST/依赖审计）。

## 四、横向「可改善空间」总结（最值得投入的方向）

1. **测试深度**：目前全是**单元测试 + mock prisma**（约 275 例），**没有集成/E2E**。repo 层多租户 scoping 靠断言 `where` 形状，缺真实 D1 端到端验证；UI 无 Playwright/视觉回归。两次「严重数据级 bug」（#130 级联删提交、IDOR #192）都是事后补测——**引入一层针对 D1 的集成测试 + 关键流程 E2E**，是回报最高的投入。
2. **授权策略集中化**：IDOR 修了两次（#28、#192）。可把「按角色/租户 scope」抽成**统一策略 + 默认拒绝 + 全覆盖回归**，而非逐 finder 加 `teacherId`。
3. **运行时可观测性**：有 `wrangler tail` + observability，但无错误聚合（Sentry 类）、无前端性能/真实用户监控。线上问题目前靠日志人肉排查。
4. **CI 门禁**：只有 lint+tsc+test+build，无 SAST、依赖漏洞扫描（Dependabot）、bundle 体积预算、a11y 自动检查（axe）。
5. **AI 层**：模型 id 写死会过期；置信度阈值/逐句权重是经验值，**缺真实数据闭环校准**；provider 失败的可观测性较弱。
6. **时区/日期**：反复出 bug（#73/74/75/161/171）后已统一，但建议沉淀为「一处时区工具 + 测试」长期守护。
7. **内容/i18n**：UI 三语但题库内容仅中/英；2000 句回填用 7 个 PR，数据录入类工作建议脚本化。
8. **刻意的取舍**（非缺陷，备查）：原生 Cloudflare Queues/DO 有意不做（可验证性优先）；定时任务走 Actions cron（分钟级漂移）；邮箱验证取消（易用优先）；防作弊仅前端提示。
9. **流程**：4 天 209 PR、单 PR 极小——利于 review，但部分（中文回填、页面标题、加载骨架）可合并；末段已明显边际递减，**更值得由产品方向驱动而非自主凑增量**。

## 五、一句话结论

4 天内从 0 到一个**功能完整、架构分层干净、安全/可访问性/运维都收口**的多租户教育应用；最大的结构性短板是**缺集成/E2E 测试与运行时可观测性**，这也是下一步投入回报最高的地方。
